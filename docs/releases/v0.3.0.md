# mockryx v0.3.0

## Breaking

Against v0.2.x, the rule for the two key files changes. The files are `--client-key-file` (or `$MOCKRYX_CLIENT_KEY_FILE`) and `--api-key-file` (or `$MOCKRYX_API_KEY_FILE`, new in this release). A key file now follows the owner rule that PostgreSQL applies to the private key a server loads.

- A key file you own must be a regular file with mode `0600` or stricter. A file you own at `0644` is refused before any request is sent, with exit `2`. It worked in v0.2.x.
- A key file owned by root must be `0640` or stricter, and it may not be group-writable. A root-owned `0440` or `0640` file is accepted.
- A key file owned by any other account is refused, even at `0600`.

## Migration

- A key file you own at `0644`: run `chmod 600 <file>`. The key itself does not change.
- A key file owned by another account: make it owned by the account that runs mockryx, with `0600`, or make it root-owned at `0440` or `0640`.
- A Kubernetes Secret mounted with an `fsGroup`: nothing to change. The root-owned `0440` or `0640` file is accepted. Keep the pod non-root; the image runs as uid 65532. A root process compares the owner with itself first, so a root-owned file must then be `0600`.
- Windows: the owner and mode check is not made, because Go reports a writable file there as 0666 whatever its ACL says. The file must still be a regular file, and a key file readable by other Windows users is accepted. Protect it with its ACL instead.

## What changed since v0.2.2

- **The x-api-key can come from a file.** `--api-key-file PATH` or `$MOCKRYX_API_KEY_FILE` reads the key from a one-line file under the same owner rule as the client key file. The environment names the file when no flag does. A file is the preferred source, because the key stays off the process list. A key file given together with a key value (`--api-key` or `$MOCKRYX_API_KEY`) is a usage error, exit `2`, before any request is sent.
- **`--api-key` still works, with a warning.** A key on the command line is sent as before. mockryx writes one line to stderr that names the flag and never prints the value.
- **The x-api-key is masked out of findings, reports and events.** The client key was already masked; the x-api-key was not. A gateway that echoed the key back in a header or in its body could put it into the human and JSON reports, the saved report and the events file. None of them carries it now.
- **Key file errors never print the contents.** A refusal names the path and the mode or the owner, and never the key.
- **agent-stack-go v2.0.1 (#78).** A dependency bump. Nothing in mockryx's own surface moves with it.
- **v0.2.2 upgrade section (#79).** A documentation commit after the v0.2.2 tag. It describes the event stream file mode that v0.2.2 already shipped. No code change.

## Evidence and limit

- 225 test functions (README badge 225). 38 scenarios across three feature files, each bound to a named test, 0 broken. The owner rule is tested with an injected file mode and owner, so those cases run without privilege.
- Gates run on the release commit are listed in the release PR description.

## Not proven

- A Kubernetes Secret mount on a cluster: not run. The root-owned case is tested with an injected owner, not by a root process.
- Windows: the owner and mode check is not made, and the Windows branch is tested with an injected operating system, not on a Windows host.
- Masking is an exact string match on the key. A gateway that echoes the key transformed (base64, URL-encoded, split across headers, or lower-cased) would not be masked.
- No live run against a gateway in this release.
