# mockryx v0.4.0

A minor release on v0.3.1. It adds three game-day drills for an LLM provider that is up but failing, and the local stand-in provider they run against. Nothing changes for an existing run: no flag, exit status, `Finding` semantics, scenario format or file format moves, and `mockryx run ./scenarios` does not load the new drills.

## Added

- **Three provider-failure drills (#87).** `scenarios/game-day/provider-5xx.yaml`, `provider-rate-limited.yaml` and `provider-timeout.yaml` join `provider-outage.yaml`. Each sends the operator's own gateway a call and checks the chain in its order:
  1. The call comes back with the provider's own status: 503, 429 or 504.
  2. The gateway puts a `dependency_failed` for that run on the bus (`expect.event`, source `tokenfuse`).
  3. The run reaches a person (`expect.event`, source `heraldyx`, type `alert_sent`).
  A `Finding` names the link that is missing: the status the agent received, the event the bus never carried, or the notice nobody sent. The drills use the existing event check only, add no scenario capability, and declare no `requires:`, so a miss is a `Finding` and never a skip.
- **A local stand-in provider.** `internal/providerstub` and `scripts/provider-stub.go`, run with `go run`. It answers every request with a 503, a 429 (with a `Retry-After`) or a 504 after a delay, and the delay is at most ten seconds, under mockryx's own fifteen-second client timeout. It listens on loopback only: any other address is refused before binding, with exit status 2. It makes no outbound call, which a source scan checks. The script is excluded from the build, so the repository still builds one binary.

## Upgrade

Pull `ghcr.io/taipanbox/mockryx:v0.4.0` in place of `v0.3.1`, or download the binary for your platform from this release. No setting, stored state or wire format changes, so there is nothing to migrate. To roll back, run v0.3.1 again.

The game-day drills sit outside `scenarios/` on purpose, in `scenarios/game-day/`, and are run deliberately for the length of a scheduled game day. A failing provider sends no `x-fuse-*` header, so `requires:` cannot tell a gateway that is not configured from an upstream the operator has not broken today, and a routine CI run would show a false gap on any ordinary day.

## Evidence

- `internal/runner/gameday_test.go` runs each drill through a model of the chain: the stub, a gateway that passes the status through and writes `dependency_failed` to a hash-chained file, and a notifier that writes `alert_sent`, read back by the real `internal/watch`. All three pass with the chain whole. Each fails on the status when the gateway hides the failure, on `tokenfuse/dependency_failed` when the bus is silent, and on `heraldyx/alert_sent` when nobody is told.
- Every new test was run against a planted fault first and went red: eight faults in the stub and four in the drills.
- `scripts/selftest.sh` has a game-day section in which every run comes back failed against a gateway that answers 200 to everything, and `scripts/gates-have-teeth.sh` has a case that plants a game-day drill that cannot fail.
- CLAUDE.md invariant 16, twelve scenarios in `features/provider-failure-game-day.feature` each bound to a test, a README game-day section, and a `VALIDATION.md` record. 240 test functions.
