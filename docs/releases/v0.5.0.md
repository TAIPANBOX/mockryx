# mockryx v0.5.0

A minor release on v0.4.0. It adds a drill for the tool hold both stacks put on a tool call nothing grants, and a key of the MCP broker's own, so the broker drills can run against a broker that requires one. Nothing changes for an existing run that sets neither: no exit status, `Finding` semantics or scenario format moves, and with no broker key the broker is sent none, as before.

## Added

- **A broker key of its own (#93, invariant 19, estate-gates GAPS G4.10).** `--mcp-broker-key-file PATH` or `$MOCKRYX_MCP_BROKER_KEY_FILE` (preferred), or `$MOCKRYX_MCP_BROKER_KEY`. No flag takes the value, so it stays off argv, and setting both is a usage error. The file follows the client key file's owner rule, and an error never repeats its contents. The key is sent as `x-fuse-key` on the broker's JSON-RPC call only: never to the gateway's `messages` and `tool_check` routes, and never on the `/healthz` reachability probe. The same secret as the gateway client key is refused before anything is sent (exit 2), so invariant 13 stands: the gateway's client key still reaches no service the operator did not give it to. The key is masked as `***` in every Finding, report, saved file and event. `components.json` declares the two new variables.
- **The tool hold, rehearsed (#91, invariant 18).** `scenarios/mcp/mcp-ungranted-tool-held.yaml` sends the same call as `agent://ungranted.invalid/rehearsal/no-grant` and as `agent://mockryx.local/rehearsal/tool-hold`. The first must come back `-32004` naming `when_no_grant`; the second must come back a result, so a broker that holds everybody fails too. It uses an `mcp` step and two existing `expect` fields, and adds no scenario capability. Every shipped drill is held to the prefix the stacks' `grant-drills` rule reaches.

## Fixed

- **A broker's refusal reaches a report whole (#91).** A real approval id is 35 bytes, and the 120 bytes kept of `got` cut the reason off mid-word.
- **CI gates that read a pipe now see the pipes that end early (#90, invariant 17).**

## Upgrade

Pull `ghcr.io/taipanbox/mockryx:v0.5.0` in place of `v0.4.0`, or download the binary for your platform from this release. No setting, stored state or wire format changes, so there is nothing to migrate. To roll back, run v0.4.0 again.

To run the broker drills against a broker that sets `TOKENFUSE_MCP_KEYS`, give mockryx one of that broker's keys in a file and point `$MOCKRYX_MCP_BROKER_KEY_FILE` at it. The broker must also admit the key under its own rules: under `TOKENFUSE_AGENT_TOKENS=require` its id must be listed in `TOKENFUSE_MCP_AGENT_TOKENS_STATIC_KEYS`.

## Evidence

- `features/mcp-broker-key.feature`, ten scenarios, and `features/tool-hold.feature`, eight, each bound to a test (`scripts/features-are-bound.sh`).
- Every new test was run against a planted fault first and went red: four mutants for the broker key (the key sent to the gateway, the client key sent to the broker, the key unmasked, the key on the health probe) and seven for the hold drill.
- The hold drill was run against wardryx v2.6.0 and TokenFuse v1.23.0 from their published images, with the floor and `grant-drills`, with the floor and no grants, and with the starter rules only; each run came back as the policy predicts. `VALIDATION.md` has the record.
- 262 test functions; `scripts/gates-have-teeth.sh` runs 53 cases.
